# Plan 29.2: Lift Filter-Only Gate for Dual-Exec Advance

<objective>
When `ZERO_DUAL_EXEC` is enabled, remove the `filter-only` operator restriction in `#reevaluateRustAdvance()` so that ALL operator types (join, exists, take, etc.) get dual-exec compared. The companion pipeline check and unique key check remain unconditionally.
</objective>

## Task 1: Modify `#reevaluateRustAdvance()` to bypass filter-only gate

<read_first>

- `pipeline-driver.ts:1005-1023` — current `#reevaluateRustAdvance()` implementation
- `pipeline-driver.ts:1240-1330` — the `#dualExecAdvance()` method that runs when `#useRustAdvance` is true and `isDualExecEnabled` is true
- `pipeline-driver.ts:1029-1100` — the `#rustDispatchAdvance()` method
- Confirm `isDualExecEnabled` is imported
  </read_first>

<action>
Modify `#reevaluateRustAdvance()` to conditionally skip the filter-only operator check when dual-exec is enabled. The new logic:

```typescript
#reevaluateRustAdvance() {
  this.#useRustAdvance =
    USE_RUST_ADVANCE &&
    this.#pipelines.size > 0 &&
    this.#pipelineConfigs.size === this.#pipelines.size &&
    // When dual-exec is enabled, allow ALL operator types through
    // so they get compared. In production (non-dual-exec), restrict
    // to filter-only since that's what Rust supports.
    (isDualExecEnabled ||
      [...this.#pipelineConfigs.values()].every(c =>
        c.operators.every(op => op.type === 'filter'),
      )) &&
    // Rust advance cannot monitor companion pipelines (scalar subquery
    // change detection requires pushing through TS IVM).
    [...this.#pipelines.values()].every(
      p => p.companions.length === 0,
    ) &&
    // Rust fan-out is stateless per-change and cannot correctly handle
    // unique key conflicts that span multiple diff entries.
    [...this.#tableSpecs.values()].every(
      s => s.tableSpec.uniqueKeys.length <= 1,
    );
}
```

Key changes:

- The `every(op => op.type === 'filter')` check is wrapped in `(isDualExecEnabled || ...)`
- When `isDualExecEnabled` is true, the short-circuit makes the operator check pass for any type
- The companion check and unique key check remain unconditional
- In `#dualExecAdvance()`, both TS and Rust paths run and are compared, so non-filter operators will surface mismatches (which is exactly the point)
  </action>

<acceptance_criteria>

- When `ZERO_DUAL_EXEC` is set, queries with joins/exists/take operators pass the gate
- When `ZERO_DUAL_EXEC` is unset, only filter-only queries pass (existing behavior preserved)
- Companion pipeline check still unconditionally applies
- Unique key check still unconditionally applies
  </acceptance_criteria>
