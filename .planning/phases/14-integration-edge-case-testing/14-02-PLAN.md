# Plan 14-02: Edge Case Tests

<objective>
Add comprehensive edge case coverage across four categories: diff size extremes, data type boundaries, pipeline topology changes, and error/fallback paths. Rust unit tests validate internal logic; a new TS integration harness validates Rust-vs-TS output parity end-to-end.
</objective>

<must_haves>
- Rust unit tests for empty diffs, 1000+ row diffs, single-row diffs, all-no-op diffs
- Rust unit tests for NULL, empty string, unicode, very long strings, blob, real, integer values in rows
- TS integration test file `pipeline-driver.edge-cases.test.ts` exists with tests for mixed eligible/ineligible pipelines and add/remove pipelines mid-advance
- TS integration tests for error paths: version_mismatch retry, graceful fallback on Rust error
- `cargo test` in zqlite-rs passes with new tests
- `vitest` passes on the new edge case test file
- No existing test files or source files modified
</must_haves>

Append new tests to the `#[cfg(test)] mod tests` block in `packages/zqlite-rs/src/advance.rs`. Add these tests after the existing `test_process_change_skip_unrelated_table` test:

1. `test_empty_diff` — create a pipeline with source_tables=["users"], pass an empty `changes: Vec<Change>` to `process_pipeline`. Assert result is empty vec.

5. `test_large_diff_filtered` — 1000 Changes to "users" table with `active` field alternating true/false. Pipeline has filter `{op: "eq", field: "active", value: true}`. Assert result.len() == 500.

Each test should use `PipelineConfig` and `Change` structs directly (no DB needed). Pattern matches existing tests in the file.

IMPORTANT: Only APPEND to the existing `mod tests` block. Do NOT modify or reorder existing tests.
</action>

<task id="2">
<title>Add Rust unit tests for data type edge cases</title>
<read_first>
- packages/zqlite-rs/src/advance.rs
- packages/zqlite-rs/src/diff.rs
</read_first>
<action>
Append additional tests to the `mod tests` block in `packages/zqlite-rs/src/advance.rs`:

1. `test_null_value_in_row` — Change with next_value containing `{"id": "u1", "name": null}`. No filter. Assert produces "add" with row containing null value.

2. `test_empty_string_value` — Change with next_value `{"id": "u1", "name": ""}`. Assert row["name"] == json!("").

3. `test_unicode_values` — Change with next_value `{"id": "u1", "name": "\u{1F600}\u{4E16}\u{754C}"}` (emoji + CJK). Assert produces "add" and row contains the unicode string.

4. `test_very_long_string` — Change with next_value where "name" is a 100_000 character string (repeat "a" 100000 times). Assert produces "add" and the row's name field length matches.

5. `test_integer_value` — Change with next_value `{"id": "u1", "count": 42}`. Assert row["count"] == json!(42).

6. `test_real_value` — Change with next_value `{"id": "u1", "score": 3.14159}`. Assert row["score"] is a number.

7. `test_filter_with_null_field` — Pipeline with filter `{op: "eq", field: "active", value: true}`, Change where "active" is null. Assert filtered out (0 results).

8. `test_filter_with_missing_field` — Pipeline with filter on field "active", Change where the field doesn't exist in the row. Assert filtered out (0 results).

Each test uses in-memory structs only. Pattern: create PipelineConfig, create Change, call process_change_for_pipeline, assert results.

IMPORTANT: Only APPEND to the existing `mod tests` block.
</action>
