<objective>
Flip the production view-syncer consumer from the buffered streaming API to the per-pipeline streaming API so `pokers.pokePart` fires as fast pipelines complete (mid-batch) instead of only at end-of-batch. CVR commit semantics, `pokers.end`, and `pokers.cancel` on `ResetPipelinesSignal` are preserved exactly. Migration is gated by the `ZQLITE_RS_USE_STREAMING_CONSUMER` env var (default `true`) so an operator can roll back via service restart without a code revert.

Purpose: Make Phase 31's streaming surface visible to clients. Today, v4.0's rayon parallelism reduces total wall time but NOT time-to-first-byte — clients still wait for the slowest pipeline because everything is materialized into one Buffer before returning to JS. Per-pipeline streaming changes that for the first production consumer.

Output:

- `view-syncer.ts` consumes `advanceStreaming` + `addQueriesStreaming` (with a `ZQLITE_RS_USE_STREAMING_CONSUMER=false` fallback to the existing buffered methods).
- `#processChanges` consumes `AsyncIterable<RowChange | 'yield'>`.
- `RustStreamError` is logged with kind/message/source and re-thrown (no per-kind recovery in view-syncer).
- Two new test files: mid-batch pokePart timing (MIGRATE-03) and ResetPipelinesSignal cancel (MIGRATE-04).
- `connectWithQueueAndSource` extended with optional `onMessage` callback for timestamp recording.
- All existing tests continue to pass under both flag values.
  </objective>
