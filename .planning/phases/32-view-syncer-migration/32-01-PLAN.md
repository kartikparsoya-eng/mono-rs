RESEARCH §4 locks the fix shape as "return BigInt for out-of-range values" (correct, bit-exact, no information loss) rather than throwing. Tasks 1 & 2 implement this disambiguated semantics; behavior block in each task documents the rationale.

Fix the pre-existing CR-01 i64 decoder bug in `decode-advance-buf.ts::readJsonValue` BEFORE Phase 32-02 migrates the production view-syncer onto the streaming chunk decoder. The current code multiplies `hi * 0x100000000 + lo` (lossy in f64 once `|hi| >= 2^21`) and only THEN compares against `MAX_SAFE_INTEGER`, defeating the guard. The fix gates on `hi` magnitude before the lossy arithmetic.

Purpose: Phase 32 is the first production exposure of the streaming chunk decoder; the buffered decoder has shipped with this latent bug since v4.0 but was masked by typical i64 values staying within safe range. Shipping CR-01 first ensures both prod paths (buffered + streaming) ship with a correct decoder.

Output: Two-line fix in `decode-advance-buf.ts` + 6 boundary regression tests in `decode-advance-buf.test.ts`. No view-syncer changes in this plan.

Fix shape (per RESEARCH §4 + CONTEXT D-12..D-13):

```typescript
case 1: {
  // i64. Gate on hi magnitude BEFORE Number arithmetic (CR-01 fix per D-12..D-13).
  // 2^53 = 2^21 * 2^32, so |hi| >= 2^21 (= 0x200000) means the value
  // exceeds MAX_SAFE_INTEGER and JS Number arithmetic loses precision.
  // Construct BigInt directly in that case.
  const lo = view.getUint32(offset, true);
  const hi = view.getInt32(offset + 4, true);
  offset += 8;
  if (hi >= 0x200000 || hi <= -0x200000) {
    return [BigInt(hi) * 0x100000000n + BigInt(lo), offset];
  }
  return [hi * 0x100000000 + lo, offset];
}
```
