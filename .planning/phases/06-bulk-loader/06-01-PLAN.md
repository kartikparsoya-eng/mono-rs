1. Create a test table with 10 columns (matching typical initial-sync schema):

```sql
CREATE TABLE bench_sync (
  id TEXT PRIMARY KEY,
  col1 TEXT, col2 TEXT, col3 TEXT,
```

2. Generate test data: 10,000 rows of flat values (100,000 total values in a flat array).

3. Prepare the batch INSERT statement (batch size 50):

```sql
INSERT INTO bench_sync VALUES (?,?,?,?,?,?,?,?,?,?),(?,?,?,?,?,?,?,?,?,?),...  -- ×50
```

4. Measure **Pattern A: N/50 napi crossings** (current behavior):
   - Loop: for i=0; i < 10000/50; i++ → stmt.run(flatValues.slice(i*500, (i+1)*500))
   - Time the entire loop (this is what flush() does today)

5. Measure **Pattern B: Single bulkInsert call** (hypothetical Rust method):
   - For now, since bulkInsert doesn't exist yet, measure the THEORETICAL minimum:
   - Time a single stmt.run() call × 1 with 50 rows, then calculate: (total_time - per_call_overhead \* (N/50 - 1))
   - Per-call overhead = measured from a no-op prepare+finalize cycle

6. Calculate and report:
   - `total_flush_time` = Pattern A total ms
   - `per_call_overhead` = average overhead per napi crossing (measure 1000 empty runs to get baseline)
   - `napi_overhead_pct` = (per*call_overhead * num*calls) / total_flush_time * 100
   - Print: "napi overhead: X.X% of flush time"
   - Print D-19 decision: "<5% → SKIP Phase 6" or "5-15% → flush-only Rust" or ">15% → full Rust bulk INSERT"

7. Run each measurement 5 times, report median.

Use both `RustDatabase` and `BetterSqlite3` to compare INSERT throughput at scale.
