# Plan 01: Rust Filter Predicate Evaluator

<objective>
Implement the Filter operator's predicate evaluation in Rust. Given a batch of IVM changes and a serialized predicate AST, evaluate which changes pass the filter and return the filtered set. Handle EDIT splitting (old matches but new doesn't → remove; old doesn't but new does → add).
</objective>

<tasks>

2. Define `Predicate` enum (the AST):

```rust
#[derive(Clone, Debug)]
pub enum Predicate {
    Eq(String, Value),         // field == value
    Neq(String, Value),        // field != value
    Gt(String, Value),         // field > value
    Gte(String, Value),        // field >= value
    Lt(String, Value),         // field < value
    Lte(String, Value),        // field <= value
    In(String, Vec<Value>),    // field IN (values)
    Like(String, String),      // field LIKE pattern
    IsNull(String),            // field IS NULL
    IsNotNull(String),         // field IS NOT NULL
    And(Vec<Predicate>),       // AND conditions
    Or(Vec<Predicate>),        // OR conditions
    Not(Box<Predicate>),       // NOT condition
}
```

4. Implement LIKE pattern matching (SQL LIKE with % and \_ wildcards)

5. Implement `compare_values(a: &Value, b: &Value) -> Ordering` matching JS `compareValues` from data.ts (UTF-8 string comparison, null < everything)
   </action>

## Task 2: Implement napi Binding for Filter Push Batch

<read_first>

- packages/zqlite-rs/src/database.rs (for napi patterns)
- packages/zql/src/ivm/change.ts
- packages/zql/src/ivm/change-type-enum.ts
- packages/zql/src/ivm/change-index-enum.ts
  </read_first>

<action>
Add napi-exposed function in `packages/zqlite-rs/src/filter.rs`:

```rust
use napi::bindgen_prelude::*;
use napi::{Env, JsObject, JsUnknown};

/// Change types matching TS: ADD=0, REMOVE=1, EDIT=2, CHILD=3
const CHANGE_ADD: u32 = 0;
const CHANGE_REMOVE: u32 = 1;
const CHANGE_EDIT: u32 = 2;
const CHANGE_CHILD: u32 = 3;

#[napi]
pub struct RustFilterPredicate {
    predicate: Predicate,
}

#[napi]
impl RustFilterPredicate {
    #[napi(constructor)]
    pub fn new(predicate_json: String) -> Result<Self> {
        // Parse JSON AST into Predicate enum
        let predicate: Predicate = serde_json::from_str(&predicate_json)
            .map_err(|e| Error::from_reason(format!("Invalid predicate: {}", e)))?;
        Ok(Self { predicate })
    }

    /// Evaluate a batch of changes. Returns indices of changes that pass.
    /// For EDIT changes that need splitting, returns split info.
    #[napi]
    pub fn filter_push_batch(&self, env: Env, changes: Vec<JsUnknown>) -> Result<JsObject> {
        // Returns: { passed: number[], splits: {index: number, type: 'add'|'remove'|'both'}[] }
        // - passed: indices of changes that pass through unchanged
        // - splits: EDIT changes that need splitting (old matched but new didn't, or vice versa)
    }
}
```

The key insight: instead of materializing full Change objects in Rust, we:

1. Receive changes as JsUnknown array
2. For each change, extract just the row fields needed by the predicate
3. Return which indices pass and which EDITs need splitting
4. TS wrapper uses these indices to build the output change array (preserving relationships)

This avoids marshalling relationships through napi entirely.
</action>
