phase). This is a child-driven inner join that produces parent rows with
attached children, in parent-input sort order, with overlay semantics that

This wave depends on Wave 2 — UnionFanIn dedup-merge and the
InProgressOverlay pattern. FlippedJoin uses both.

  <behavior>
    - **Fetch algorithm:**
      1. Translate parent constraint to child constraint using parent_key↔child_key index map. (TS lines 127-137)
      2. Fetch all child nodes via constrained child.fetch.
      3. If `in_progress_child` is REMOVE, splice the removed node back into childNodes at its sorted position (TS 158-165 — overlay-undo).
      4. For each child, build a parent-side constraint (`build_join_constraint(child_row, child_key, parent_key)`).
      5. For each non-empty constraint, fetch parent.fetch with merged constraint; collect into `Vec<Vec<Node>>` (one stream per child).
      6. Run k-way merge in parent's compareRows order:
         - Maintain cursor `Vec<usize>` per child stream.
         - Pop the minimum parent across all current cursors.
         - Collect ALL child indexes whose current parent equals the min (multiple children can share a parent in N:1).
         - For the min parent, build relatedChildNodes from those child indexes.
         - Apply overlay (lines 247-284) — see overlay sub-action below.
         - If overlaid relatedChildNodes is non-empty, emit `Node { row: min_parent.row, relationships: { rel_name: overlaid_children } }`.
      7. Continue until all cursors exhausted.
    - **Overlay rules** (TS 247-284):
      - If `in_progress_child` is set AND `is_join_match(in_progress.row, child_key, min_parent.row, parent_key)`:
        - Compute `has_been_pushed_for_min_parent = parent_schema.compare_rows(min_parent.row, in_progress.position) <= 0`.
        - If REMOVE and has_been_pushed: filter out the in-progress node from relatedChildNodes (it was spliced back in by step 3 but now it's already-pushed-past).
        - If !REMOVE and !has_been_pushed: apply `generate_with_overlay` (insert/edit) to the relatedChildNodes.
      - Otherwise overlaid = relatedChildNodes unchanged.
  </behavior>

    - **push_child(change):**
      - Add/Remove → `push_child_change(change, exists=false)`.
      - Edit → assert key unchanged via `row_equals_for_compound_key`; `push_child_change(change, exists=true)`.
      - Child → `push_child_change(change, exists=true)`.
    - **push_child_change(change, exists?):**
      1. Set `self.in_progress_child = Some(InProgressOverlay { change, position: None })`.
      2. Build constraint over child_key→parent_key. If None (NULL), parents stream is empty.
      3. Fetch parents via parent.fetch(constraint).
      4. For each parent_node:
         - Update `self.in_progress_child.position = Some(parent_node.row.clone())`.
         - Build constraint parent_key→child_key for fetching this parent's children.
         - If `!exists`: scan `child.fetch(constraint)` and check if there's any other child node ≠ change.node — if yes set exists=true.
         - If exists (after the scan or already true): emit Change::Child {parent: parent_node-with-relationship, child_data: {relationship_name, change}}.
         - Else: emit Change::Add or Change::Remove (matching the change's type) with parent-and-relationship-{change.node alone}.
      5. After loop, clear `self.in_progress_child = None`.
  </behavior>

    - **push_parent(change):**

      2. Check has_related_child by scanning `child_node_stream(change.node())` for any node — short-circuit on first.
      3. If !has_related_child, return vec![] (inner-join semantics).
      4. Switch on change type:

         - Remove → emit Change::Remove { node: flip(change.node) }
         - Child → emit Change::Child { node: flip(change.node), child_data: change.child_data }
         - Edit → assert keys unchanged; emit Change::Edit { node: flip(change.node), old_node: flip(change.old_node) }
       where `flip(node)` adds `relationships: { rel_name: child_node_stream(node) }` to node.
  </behavior>
