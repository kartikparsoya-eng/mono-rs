# Plan 27-02: TS Coordinator + View-Syncer Integration

<objective>
Integrate `rust_dispatch_poke` into the view-syncer advance path. Add a `ZERO_DISABLE_RUST_DISPATCH` feature flag. When enabled, the advance path collects pipeline configs from the current ViewSyncer and calls `rustDispatchPoke` instead of `rustFanOut`. The `timeSliceQueue` is bypassed for the advance path when Rust dispatch is active.
</objective>

<task id="01">
<title>Add rustDispatchPoke binding in pipeline-driver.ts</title>
<read_first>
- packages/zero-cache/src/services/view-syncer/pipeline-driver.ts (lines 57-85 for existing rust bindings)
- packages/zqlite-rs/index.d.ts (rustDispatchPoke declaration)
</read_first>
<action>
In `pipeline-driver.ts`, add a binding for `rustDispatchPoke` following the same pattern as `rustAdvanceFn` / `rustFanOutFn`:

1. Add type: `type RustDispatchPokeFn = (changesJson: string, vsPipelinesJson: string) => Buffer;`
2. Add variable: `let rustDispatchPokeFn: RustDispatchPokeFn | undefined;`
3. In the try/catch block that loads `zqlite-rs` bindings (~line 77-85), add: `rustDispatchPokeFn = bindings?.rustDispatchPoke;`
4. In the catch block, set it to undefined
5. Add env flag check: `const DISABLE_RUST_DISPATCH = process.env.ZERO_DISABLE_RUST_DISPATCH === '1' || process.env.ZERO_DISABLE_RUST_DISPATCH === 'true';`
   </action>
   <acceptance_criteria>

- `pipeline-driver.ts` contains `let rustDispatchPokeFn: RustDispatchPokeFn | undefined`
- `pipeline-driver.ts` contains `rustDispatchPokeFn = bindings?.rustDispatchPoke`
- `pipeline-driver.ts` contains `ZERO_DISABLE_RUST_DISPATCH`
  </acceptance_criteria>
  </task>

<task id="02">
<title>Add #rustDispatchAdvance method to PipelineDriver</title>
<read_first>
- packages/zero-cache/src/services/view-syncer/pipeline-driver.ts (#rustAdvance method at line 988)
- packages/zero-cache/src/services/view-syncer/decode-dispatch-buf.ts (new decoder)
</read_first>
<action>
Add a new method `#rustDispatchAdvance(vsId: string)` to the `PipelineDriver` class. This method:

1. Checks `rustDispatchPokeFn` is available and `!DISABLE_RUST_DISPATCH`
2. Runs TS diff (same as `#rustAdvance`): `const diff = this.#snapshotter.advance(...)`
3. Collects changes from diff iterator into `collectedChanges` array
4. Builds the VS pipelines JSON: `[{vs_id: vsId, pipelines: [...this.#pipelineConfigs.values()]}]`
5. Calls `rustDispatchPokeFn(changesJson, vsPipelinesJson)`
6. Decodes result with `decodeDispatchPokeBuf`
7. Finds the result for this VS ID
8. If error, throws `ResetPipelinesSignal`
9. Converts decoded changes to `RowChange` objects using existing `#convertDecodedChanges`
10. Updates table DBs (same as `#rustAdvance` post-processing)
11. Returns `{version, numChanges, changes}` same as `#rustAdvance`

In `processTransaction()` (the public advance entry point), add a check before the existing `#rustAdvance` path:

- If `rustDispatchPokeFn && !DISABLE_RUST_DISPATCH && this.#allFilterOnly`, call `#rustDispatchAdvance(vsId)` instead
- The `vsId` parameter needs to be threaded through from the ViewSyncer — add it as a parameter to `advance()` and `processTransaction()`
  </action>
  <acceptance_criteria>
- `pipeline-driver.ts` contains method `#rustDispatchAdvance`
- Method calls `rustDispatchPokeFn` with changes and VS pipeline configs
- Method uses `decodeDispatchPokeBuf` to decode results
- `processTransaction` has a code path that calls `#rustDispatchAdvance`
  </acceptance_criteria>
  </task>

<task id="03">
<title>Thread VS ID through advance path and bypass timeSliceQueue</title>
<read_first>
- packages/zero-cache/src/services/view-syncer/view-syncer.ts (#advancePipelines at line 2172, timeSliceQueue at line 2435)
- packages/zero-cache/src/services/view-syncer/pipeline-driver.ts (advance method)
</read_first>
<action>
1. In `pipeline-driver.ts`, add `vsId: string` parameter to the `advance(timer)` method signature (or add a `setVsId(id: string)` setter)
2. In `view-syncer.ts` `#advancePipelines`:
   - Pass `this.id` (the ViewSyncer's client group ID) to `this.#pipelines.advance(timer)` or set it before calling
3. For `timeSliceQueue` bypass: In the `yieldProcess` function or the `TimeSliceTimer`, add a check: if Rust dispatch is active (the advance was handled by `rustDispatchPoke`), skip the `timeSliceQueue.withLock()` call since CPU work already happened off the main thread
   - One approach: have `#rustDispatchAdvance` return changes that DON'T include `'yield'` markers, so `#processChanges` never hits the yield path
   - The existing `#rustAdvance` already returns a non-yielding iterable — `#rustDispatchAdvance` should follow the same pattern
4. Add `ZERO_DISABLE_RUST_DISPATCH` to the env config documentation/logging on startup
</action>
<acceptance_criteria>
- `view-syncer.ts` passes VS ID to pipeline advance path
- When Rust dispatch is active, no `timeSliceQueue.withLock()` calls occur during advance
- `ZERO_DISABLE_RUST_DISPATCH=1` falls back to existing `#rustAdvance` path
- Existing pipeline-driver tests still pass (they use single-VS mode which is compatible)
</acceptance_criteria>
</task>
