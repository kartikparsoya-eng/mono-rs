<objective>
Fix AUDIT-03 (Risk #2 from `.planning/IVM-PORT-AUDIT.md`): Five `debug_assert!` / `debug_assert_eq!` calls protect framework invariants but are stripped in release builds. When upstream logic (e.g. split_edit_keys) fails, the operator silently produces wrong output instead of panicking. Promote them to `assert!` / `assert_eq!`. Add a `#[should_panic]` regression test per promoted assertion.

Purpose: These invariants encode "this should never happen if the framework is correct." A silent miscalculation downstream is a worse failure mode than a loud panic — TS uses runtime asserts here for exactly this reason. Promoting also makes Bug #2-class regressions (Plan 02) loud rather than silent if they ever recur.

Output: 5 specific debug_assert sites promoted to assert in 4 files, plus 5 `#[should_panic(expected = "...")]` tests that confirm the assertions fire in release builds.

**Scope discipline (per D-09):** Promote ONLY the 5 framework-invariant sites listed below. Do NOT promote unrelated `debug_assert!` calls in the same files (e.g. test-helper assertions, internal sanity checks where validation cost is excessive). Each promoted site is named with its exact line range from the audit.
