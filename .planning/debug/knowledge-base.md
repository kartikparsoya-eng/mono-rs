## phase-30-03-exists-edit-regression — IVM bench test asserts seq==par on shared pipelines, fails due to warm-up ramp bias

- **Date:** 2026-04-29
- **Error patterns:** bench_persistent_pipeline_sequential_vs_parallel, advance.rs, zqlite-rs, IVM, sequential vs parallel, assertion left=32149 right=40000, warm-up, steady state, ramp, pipeline emit count, exists_op, or_exists_op
- **Root cause:** Bench test in packages/zqlite-rs/src/advance.rs ran sequential and parallel phases on the SAME mutable pipelines vec with only one warm-up advance call. IVM operator emit count ramps from ~67 (cold) to 400 (steady state) over ~80 iterations. Sequential measured the entire ramp (total 32149); parallel ran second on already-stabilized pipelines and measured only steady state (total 40000). Assertion seq_total_changes == par_total_changes was structurally impossible by construction. Pre-existing bug, predates Phase 30 entirely (reproduces at commit aa6f0d7e2).
- **Fix:** Restructure bench_persistent_pipeline_sequential_vs_parallel to build fresh, fully-warmed (120-iter warm-up, safe margin above empirical ~80-iter convergence) pipelines for each phase. Both phases now measure 100 iterations from steady state; assertion meaningfully checks emit-count invariance under execution mode. 2.46x parallel speedup remains visible.
- **Files changed:** packages/zqlite-rs/src/advance.rs

## ivm-parity-divergences — compound OR-of-EXISTS hydrate parity 0/6 → 5/6 (B5 family)

- **Date:** 2026-05-11
- **Error patterns:** ivm-parity, regression-runner, A-nested-OR-with-EXISTS, D-simple-OR-with-EXISTS, FanOut, ParallelFanOutOperator, ParallelExistsOperator, TakeOperator, partition_key, batch_fetch_children, apply_child_operators, hydrate, EXISTS, OR-of-EXISTS, compound OR, AND-inside-OR, gate condition dropped, collect_exists_branches, build_branch_subpipeline_for_hydrate, rel_to_table, collect_child_tables, collect_rel_to_table_from_configs, uniquify_top_level_csq_aliases, alias-leak, zsubq, relationship_name, flatten_nodes_to_row_changes, coerce_row, column_types, RS returns zero rows, TS oracle, hydrate parity, zqlite-rs, zero-ivm-rs
- **Root cause:** Two distinct production bugs masked behind the same 0/6 hydrate divergence symptom — both surfaced only once compound OR-of-EXISTS branches were routed through the FanOut topology (commit 0f2361b52, B5 fix). Bug A in hydrate.rs::ParallelFanOutOperator::fetch: branch sub-pipelines built via build*operator_with_live_source → build_next_operator → ParallelExistsOperator drove EXISTS-LIMIT Take through batch_fetch_children → apply_child_operators with a default (no-constraint, no-max-bound) FetchRequest. TakeOperator::fetch on a partitioned Take with no constraint AND no max_bound returns vec![] by design (advance-mode invariant) → all EXISTS child rows silently dropped → every parent's EXISTS check saw zero children. Bug B in advance.rs::build_pipeline_state: rel_to_table was seeded from collect_child_tables(&query.ast) — the un-uniquified AST — but Phase-34 alias-leak fix (commit dc16c2588) renames every CSQ relationship to `<alias>*<count>` at config-emission time. Runtime change-output emits the uniquified name; flatten_nodes_to_row_changes lookup missed → fallback used the uniquified name as a table name → coerce_row returned None → every CSQ-EXISTS child row dropped from emitted RowChanges.
- **Fix:** Bug A — packages/zqlite-rs/src/hydrate.rs: new build_branch_subpipeline_for_hydrate(source, configs) constructs each FanOut branch via build_push_next_operator + SourceBridgeOperator (the production hydrate path), routing EXISTS through sequential ExistsOperator which issues per-parent constrained fetches and hits TakeOperator's req.constraint.is_some() branch. Bug B — packages/zqlite-rs/src/advance.rs: new collect_rel_to_table_from_configs(configs) walks the emitted OperatorConfig tree (Join, Exists, OrExists branches, FanOut branches) and keys rel_to_table by the **uniquified** relationship_name; build_pipeline_state seeds from this helper and merges AST-derived entries for `related[]` Joins.
- **Files changed:** packages/zqlite-rs/src/hydrate.rs, packages/zqlite-rs/src/advance.rs, tools/ivm-parity/regression-runner-last.json (5/6 snapshot)

## ivm-parity-d-simple — RS `NOT IN []` short-circuit ignored SQL NULL semantics (catalog 5/6 → 6/6)

- **Date:** 2026-05-11
- **Error patterns:** ivm-parity, regression-runner, D-simple-OR-with-EXISTS, NOT IN, IN, empty array, empty literal, empty set, short-circuit, NULL semantics, IS NOT NULL, isNotNull, condition_to_predicate_json, ast_to_config.rs, filter.ts, filter.rs, createPredicate, Predicate::And, empty AND, always-true, always-false, processedAt, OR with EXISTS, limit displacement, hydrate parity, zqlite-rs
- **Root cause:** `packages/zqlite-rs/src/ast_to_config.rs::condition_to_predicate_json` short-circuited `x NOT IN ()` to `{"and": []}` — an unconditional-true predicate with no field reference. The empty-AND evaluates true for any row at `packages/zero-ivm-rs/src/filter.rs:232`, bypassing the predicate's `is_null_for_row` gate (which only runs when there is a field reference). TS reference `packages/zql/src/builder/filter.ts:87-93 createPredicate` has an explicit early NULL check: if `lhs === null || lhs === undefined` it returns `false` before evaluating the operator. Net TS semantics: `x NOT IN []` ≡ `x IS NOT NULL`. RS over-permissive predicate let rows with `NULL processedAt` wrongly pass the simple branch of the `OR(EXISTS, processedAt NOT IN [])`, filling `limit=6` slots and displacing legitimate matches.
- **Fix:** Replaced the `{"and": []}` short-circuit for `NOT IN []` (column-LHS path) with `{"field": <column-name>, "isNotNull": true}` — matches TS semantics exactly. `IN []` short-circuit untouched (`{"or": []}` always-false correctly matches TS: NULL early-check returns false and non-NULL value not in empty set also returns false). Added 2 unit tests in `ast_to_config.rs::tests` that pin the contract for both `IN []` and `NOT IN []`. **Generalizable pattern:** anywhere Rust short-circuits an empty-collection operator (`IN`, `NOT IN`, `LIKE`, `BETWEEN` on empty range, etc.), it must preserve TS's NULL-on-LHS-returns-false gate by referencing the field — never emit a predicate that has no field reference and evaluates unconditionally.
- **Files changed:** packages/zqlite-rs/src/ast_to_config.rs, tools/ivm-parity/regression-runner-last.json (6/6 snapshot)

## ivm-parity-family-a-multihop-exists — nested EXISTS hydrate RS=0 because apply_child_operators dropped partition constraint and child source (1176/14/8 → 1183/7/8)

- **Date:** 2026-05-11
- **Error patterns:** ivm-parity, harness-coverage, fuzz_00782, fuzz_00985, seed_09, seed_12, seed_19, seed_23, multi-hop EXISTS, nested whereExists, 2-level EXISTS, 3-level EXISTS, RS returns zero rows, RS=0, hydrate divergence, apply_child_operators, batch_fetch_children, ParallelExistsOperator, ParallelFanOutOperator, ParallelJoinOperator, build_next_operator, build_operator_with_live_source, FetchRequest::default, partition_key, TakeOperator, take_op.rs:286-295, max_bound, EXISTS_LIMIT, apply_exists_limit, ast_to_config.rs:994, synthesize_partition_constraint, make_child_source, child-table source, outer source wrong table, SourceBridgeOperator, build_branch_subpipeline_for_hydrate, ExistsOperator sequential, hydrate.rs, zqlite-rs, Family A, partition constraint dropped, channels FanOut wrong table, conversations source threaded, 8 rows expected 0 returned, 5 rows expected 0 returned, 25 rows expected 0 returned, 11 rows expected 0 returned
- **Root cause:** Two cascading bugs in `packages/zqlite-rs/src/hydrate.rs::apply_child_operators`. (1) **Partition constraint dropped:** function called `.fetch(FetchRequest::default())` on a pipeline whose tail was the EXISTS_LIMIT `TakeOperator(partition_key=Some(child_field))` from `ast_to_config.rs::apply_exists_limit` (line 994-998). With `partition_key=Some`, `constraint=None`, `max_bound=None`, `TakeOperator::fetch` returns `vec![]` by design (take_op.rs:286-295) — every child row silently dropped → outer EXISTS sees empty child set → parent rejected → RS=0 for any 2+ level EXISTS chain. (2) **Wrong source threaded through nested operators:** `apply_child_operators` passed the OUTER `source` (e.g., conversations) into `build_next_operator`. When `child_config[1..]` contained `OperatorConfig::FanOut` or nested `OperatorConfig::Exists`, the resulting `ParallelFanOutOperator` / `ParallelExistsOperator` rebuilt sub-pipelines from this wrong source — querying conversations for branches that should hit channels. Same Bug-A "partitioned-Take-with-no-state" pattern documented in B5 (commit 0f2361b52) but at a different call site: B5 only carved around it for FanOut **branch** hydrate via `build_branch_subpipeline_for_hydrate`; the **production** hydrate path through `apply_child_operators` (called by `ParallelExistsOperator::fetch` and `ParallelJoinOperator::fetch` via `batch_fetch_children`) retained the buggy default fetch. Catalog never exercised 2+ level nesting so the bug evaded regression coverage until the 1198-AST fuzz corpus exposed it. TS reference: `packages/zql/src/builder/builder.ts:626-646 applyCorrelatedSubQuery` builds child pipeline via `buildPipelineInternal` and wraps in `Join`; surrounding `Exists` calls `Join.fetch` per-parent with a constraint — no batch shortcut.
- **Fix:** Two changes in `apply_child_operators` (same function). (1) New helper `synthesize_partition_constraint(child_config, nodes)` walks `child_config[1..]` for a Take with non-empty `partition_key` and builds a `Constraint` from `nodes[0]`'s values at those fields (all nodes in one call share a parent-group so the sample is representative). Pass into `.fetch()` → hits TakeOperator's `req.constraint.is_some()` branch and proceeds with normal initial-fetch logic. (2) Build `effective_source` via `make_child_source(source, child_config)` from `child_config[0]`'s Source variant (reuses the shared connection pool — no new SQLite connection) and pass into `build_next_operator`. Fix self-heals through nested levels: inner ParallelExistsOperator's own `batch_fetch_children → apply_child_operators` re-derives partition constraint and child source recursively. **Generalizable pattern:** anywhere RS issues a batch fetch on a sub-pipeline whose tail is a partitioned operator (Take, future partitioned aggregates), it must (a) synthesize a constraint from the parent-group's partition values and (b) ensure the source threaded through matches the **table named by child_config[0]**, not the caller's outer table.
- **Files changed:** packages/zqlite-rs/src/hydrate.rs (apply_child_operators + new synthesize_partition_constraint helper; commit e07b6634b)

## ivm-parity-family-bc-flip-scalar — RS SchemaCache PRAGMA result clobbered seeded primary_key on replica tables without PK constraints (Family C; Family B deferred)

- **Date:** 2026-05-11
- **Error patterns:** ivm-parity, harness-coverage, fuzz_00139, fuzz_00140, fuzz_00132, fuzz_00133, AND(EXISTS, EXISTS), OR(EXISTS, EXISTS), scalar:true, flip:true, RS over-include, co-1 co-2, conversations 10 vs 8, channels.where, EXISTS_LIMIT Take, TakeOperator::fetch returns all input rows instead of limit, state_with_bound, compare_rows returns Equal everywhere, empty sort, sort=[], Source.sort empty, primary_key empty, get_primary_key, SchemaCache::ensure_table_info, PRAGMA table_info, pk=0, replica lacks PRIMARY KEY, seed_primary_keys, build_pipeline_state, all_primary_keys, ast_to_config.rs, second EXISTS subquery, second get_columns clobbers seed, Zero schema PK vs SQLite PRAGMA PK, replicator copies columns not constraints, Family C, Family B, flipped CSQ in OR, applyFilterWithFlips, FlippedJoin, UnionFanOut, UnionFanIn, mergeFetches first-wins dedup, exists_op.rs or_condition, attaches children when gate matches, Phase 36, deferred
- **Root cause:** `SchemaCache::ensure_table_info` (packages/zqlite-rs/src/ast_to_config.rs ~line 165) unconditionally called `self.primary_keys.insert(table_name, pk)` with the PRAGMA-derived primary_key. On the production zero-cache replica, SQLite tables lack `PRIMARY KEY` constraints — the TS replicator copies columns from PG but not constraints — so `PRAGMA table_info` returns `pk=0` for every column and `pk_cols` is empty. The insert clobbered the explicitly seeded entry that `seed_primary_keys(query.all_primary_keys)` installs from the Zero schema in `build_pipeline_state`. Failure cascade for `channels.where(AND/OR(EXISTS(conversations), EXISTS(conversations, {scalar:true})))`: (1) seed installs conversations→["id"]; (2) first EXISTS recursion reads ["id"] OK; (3) ast_to_operator_configs then calls `get_columns("conversations")` → `ensure_table_info` → PRAGMA empty → INSERTS [] OVERWRITING seed; (4) second EXISTS recursion reads [] → Source built with `sort=[]`; (5) `apply_exists_limit` reads `Source.sort=[]` → EXISTS_LIMIT Take inherits `sort=[]`; (6) at runtime `compare_rows` (types.rs:112) returns `Equal` for every pair when sort is empty → `state_with_bound` branch in `TakeOperator::fetch` (take_op.rs ~352-372) never hits `Less` → returns ALL input rows instead of `limit`; (7) manifests as 2-row over-include (co-1, co-2) on the second EXISTS subquery (fuzz_00139, fuzz_00140). TS reference: TS reads PKs from the Zero schema (`packages/zql/src/builder/builder.ts:262 source.connect(...)` / `packages/zero-cache/src/services/view-syncer/pipeline-driver.ts`), never from SQLite PRAGMA — the equivalent failure mode does not exist on the TS side. The Rust port intentionally seeded from the Zero schema; the bug was the PRAGMA fallback wrongly clobbering that seed. **Generalizable lesson: RS replica SQLite tables do not carry PRIMARY KEY constraints from PG; any RS code that relies on PRAGMA-derived PK is broken in production. Always seed PKs from the Zero schema and treat PRAGMA as a strict fallback that never overwrites a seeded entry.**
- **Fix:** packages/zqlite-rs/src/ast_to_config.rs::SchemaCache::ensure_table_info — guard the `primary_keys.insert` so it preserves any pre-existing entry. Insert PRAGMA result only when (a) no entry exists, or (b) the existing entry is empty AND PRAGMA's result is non-empty. Verified by full hydrate corpus 1183/7/8 → 1185/5/8 (+2 OK: fuzz_00139, fuzz_00140 flipped diverge→ok), catalog regression-runner 6/6 OK (no regressions), `cargo test --lib -p zqlite-rs` 151/151, `cargo test --lib -p zero-ivm-rs` 234/234. Commit c6477e7b9.
- **Files changed:** packages/zqlite-rs/src/ast_to_config.rs (commit c6477e7b9)
- **Deferred follow-ups:** Family B (fuzz_00132, fuzz_00133 — `OR(simple_gate, csq{flip:true})`) remains diverging. Root cause is semantic: RS emits `OperatorConfig::Exists { or_condition: Some(...) }` and at runtime in `packages/zero-ivm-rs/src/exists_op.rs:155-184` attaches CSQ children when `or_condition_matches(row)` is true; TS routes flipped CSQs via `applyFilterWithFlips` (`packages/zql/src/builder/builder.ts:376-449`) using `UnionFanOut → [Filter(simple), FlippedJoin] → UnionFanIn`, and `UnionFanIn.mergeFetches` (`packages/zql/src/ivm/union-fan-in.ts:222-296`) dedups by PK keeping the FIRST yielded node — the simple-branch (relationship-less) wins so the FlippedJoin's relationship payload is discarded. Requires Phase 36 — implementing `FlippedJoinOperator` + `UnionFanOutOperator` + `UnionFanInOperator` in zero-ivm-rs (Phase 36 stub already exists at packages/zero-ivm-rs/src/flipped_join_op.rs, Wave 0 / unwired).
